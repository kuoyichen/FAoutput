What the build does (the falib rules)

打包時做了什麼（falib 規則）

  • Rule 1: 4,096 zero bytes after the last entry, so FA.EXE's 2 KB reads never run past the end of the LIB (the "random" crash in the mission builder or at mission start).
  • Rule 2: PKWare DCL compression with only what the real PKWare encoder produces: distance 2-4,095, length up to 516. Each entry is unpacked again and compared before it goes in.
  • Rule 3: the LIB and every file need a DOS 8.3 upper-case name (names are upper-cased for you).
  • A file that would compress to 90% or more of its size is stored uncompressed, as EA did (music, some sounds).
  • Entries in the FA ToolKit's order (symbols, digits, letters), with a $FALIB.INF checksum list first, so python falib.py verify can check the LIB later. The game ignores it.
  • Rule 5: if the same file is also in another LIB, the game uses the copy in the newer LIB file. Keep every file in one mod LIB only.
  • Rule 4: at most 20 LIBs for the original FA.EXE (256 for FA_BIG).
  • 規則 1：最後一個項目後面補 4,096 個 0，FA.EXE 每次讀 2 KB 時才不會讀出 LIB 結尾（任務建立或任務開始時「隨機」當掉的原因）。
  • 規則 2：PKWare DCL 壓縮，只用真正 PKWare 編碼器會產生的內容：距離 2-4,095、長度最多 516。每個項目放進去前都會再解壓一次比對。
  • 規則 3：LIB 和每個檔都必須是 DOS 8.3 大寫檔名（會自動轉成大寫）。
  • 壓縮後還有原大小 90% 以上的檔案就不壓縮直接存，和 EA 的做法一樣（音樂、部分音效）。
  • 項目照 FA ToolKit 的順序排列（符號、數字、字母），最前面放 $FALIB.INF 檢查清單，之後可以用 python falib.py verify 檢查。遊戲會忽略它。
  • 規則 5：同一個檔如果也在別的 LIB 裡，遊戲會用日期比較新的 LIB 裡的版本。每個檔只放在一個 mod LIB 裡。
  • 規則 4：原版 FA.EXE 最多 20 個 LIB（FA_BIG 可到 256 個）。
